    Install Godot & Meet the Editor

    Setting up, and understanding every panel

    ▼

    What a game engine actually is

    Before you install anything, understand what you are installing. A game engine is a framework that handles the hard, repetitive parts of making a game: drawing graphics to the screen, playing sound, detecting collisions, managing memory, and talking to your graphics card. Without one, you would write tens of thousands of lines of code just to display a single image.

    Godot gives you all of that free, plus one idea that matters more than any other: everything is a node. A node is a single building block with one job. A Sprite2D draws an image. A CollisionShape2D defines a hitbox. A Timer counts time. Combine nodes into a tree, save it, and you have a scene — which you can then reuse anywhere. That is the entire architecture, and it is the most important thing to understand on day one.

    This is exactly why Godot suits a beginner. You are not learning an engine's quirks; you are learning to snap small, well-named pieces together.

    Step 1 — Install

    1. Go to godotengine.org/download and download the Standard build for Windows. You do not need the .NET version — we use GDScript, not C#.
    2. Run the .exe. Godot is portable: no installer, no admin rights, no registry entries.
    3. The Project Manager opens. Click New Project.
    4. Name it MyFirstGame and choose a folder.
    5. Set Renderer to Compatibility — the most reliable choice for 2D and pixel art.
    6. Click Create & Edit.

    Step 2 — Learn the five panels

    The editor looks intimidating because it shows everything at once. It is really only five panels, and each has exactly one job.

    PanelWhereIts one job
    SceneTop-leftThe node tree — the structure of whatever you are building
    FileSystemBottom-leftEvery file in your project: scripts, scenes, images, sounds
    InspectorRightProperties of the selected node — position, colour, script, exports
    ViewportCentreThe visual editor: drag nodes, place sprites, build levels
    OutputBottomWhere print() lands, and where errors appear

    Step 3 — Your first scene

    1. In the Scene dock, click 2D Scene. A Node2D appears as the root.
    2. With it selected, press Ctrl+A to add a child node.
    3. Search for Label, select it, click Create.
    4. Select the Label. In the Inspector, find Text and type Hello World!
    5. Right-click the Node2D in the Scene dock → Save Scene As → save as main.tscn.
    6. Right-click main.tscn in the FileSystem dock → Set As Main Scene.
    7. Press F5. The game runs and shows your text.
    💡 Professor's Tip

    Press F1 inside the editor. This opens the Class Reference — a searchable database of every node, method, signal and property in Godot. When you wonder "what can a Sprite2D do?", press F1 and type it. This one habit will save you more time than anything else in this course.

    Nodes & Scenes

    Godot's most important concept

    ▼

    Everything is a node

    A node is a small object with a name, editable properties, and one responsibility. Nodes can have children, and a tree of nodes is a scene. Once saved, a scene behaves like a new node type you can drop into other scenes.

    Think of one node as an instrument — a guitar, a drum. A scene is the band, arranged and playing together. Your game is the concert: a menu scene, a level scene, a game-over scene, each built from reusable pieces.

    Why this matters in practice: make a coin scene once, place it forty times, and changing the coin scene updates all forty at once. That is composable design, and it is the reason Godot projects stay manageable as they grow.

    The three bodies — a distinction that matters

    These three cause more beginner confusion than anything else, so settle it now and permanently.

    NodeMoves?Blocks?Use for

    StaticBody2DNo — never movesYesWalls, floors, platforms

    CharacterBody2D and StaticBody2D physically stop each other. Area2D is a sensor: it detects but never blocks. Choosing correctly among these three is 90% of getting physics right.

    Hands-on: build three reusable scenes

    1. player.tscn

    1. New Scene → Other Node → search CharacterBody2D → rename it Player.
    2. Add child → Sprite2D. Set Texture to Godot's icon.svg.
    3. Add child → CollisionShape2D. Set Shape to a new CapsuleShape2D, then resize it to hug the sprite.
    4. Save as player.tscn.

    2. enemy.tscn — same structure, root named Enemy, using a RectangleShape2D.

    3. coin.tscn — root is Area2D, with a Sprite2D and a CircleShape2D.

    Instancing — scenes inside scenes

    Create a new scene, then drag player.tscn from the FileSystem dock into the Scene dock. It appears as a single node — an instance. Drag coin.tscn in five times and you now have five coins built from one source file. Open the coin scene, change its colour, and all five change.

    The chain-link icon in the Scene dock is the Instance button. Right-click an instance and choose Make Local to break the link for that one copy only.

    💡 Professor's Tip

    Choose a scene's root node by what the object does, not what it looks like. A coin that gets picked up is an Area2D. A wall that stops the player is a StaticBody2D. The root node is the object's identity — get it right and everything else follows.

    GDScript Basics — Variables & Functions

    Writing your first real code

    ▼

    Why GDScript, and not something else

    GDScript is Godot's built-in language. It looks like Python — indentation-based, no semicolons — but it is bound tightly to the engine, and that binding is the whole point.

    In a general-purpose language, a 2D position is just two numbers you manage yourself. In GDScript it is a Vector2: a type that already knows how to add, normalise, rotate and measure itself. The engine treats Vector2, delta, nodes and signals as first-class citizens. You write less and get more behaviour.

    The first line of almost every script is extends, and it means "this script is that node type, plus whatever I add". A script extending Label can use text, modulate and horizontal_alignment directly, then add its own functions on top.

    the first line of every script 
    extends CharacterBody2D

    Variables and types

    A variable is a named container for a value. GDScript lets you declare the type explicitly, which turns mistakes into editor warnings instead of runtime crashes.

    variables.gd 
    var player_name: String = "Parrot"   # text
var health: int = 100            # whole number
var speed: float = 250.5        # decimal number
var is_alive: bool = true     # true or false
var spawn := Vector2(100, 200)  # := infers the type

const MAX_HEALTH := 100       # never changes
const GRAVITY := 980.0
    TypeExampleUse it for
    int42Whole numbers — health, score, level
    float3.14Decimals — speed, position, timers
    String"Hello"Text — names, paths, messages
    booltrueFlags — is_alive, is_visible
    Vector2Vector2(1, 2)Any 2D position or direction
    Array[1, 2, 3]Ordered lists

    Functions

    A function is a named block of code you can call from anywhere. Write it once, use it everywhere.

    functions.gd 
    # Does something, returns nothing
func take_damage(amount: int) -> void:
    health -= amount
    if health <= 0:
        die()

# Answers something, returns a value
func calculate_score(base: int, mult: float) -> int:
    return base * mult

take_damage(10)
var s := calculate_score(100, 1.5)  # s = 150

    -> void means "returns nothing". A function that does something (damage, move, spawn) usually returns nothing. A function that answers something (distance, score, is_alive) returns a value. Getting this distinction right makes your code read like sentences rather than instructions.

    The three magic functions

    Every node has functions Godot calls for you. You never call these yourself — the engine does.

    lifecycle.gd 
    # ONCE, when the node enters the scene tree
func _ready() -> void:
    print("Ready!")

# EVERY rendered frame (~60/sec). Input, visuals, non-physics logic
func _process(delta: float) -> void:
    # delta = seconds since last frame (~0.0167 at 60 FPS)
    pass

# FIXED rate, in lockstep with physics. Anything touching velocity
func _physics_process(delta: float) -> void:
    velocity.y += GRAVITY * delta

    The rule that will save you endless bugs: if it touches velocity, it goes in _physics_process. Everything else can live in _process. _process runs at your frame rate, which varies; _physics_process runs at a fixed rate, so your character behaves identically on a slow laptop and a fast desktop.

    Two annotations that change everything

    annotations.gd 
    @export var speed: float = 300.0
# appears in the Inspector — tune without touching code

@onready var sprite: Sprite2D = $Sprite2D
# resolves the node path once the scene is ready

    @export is your tuning dial. Want to compare speed 250 against 350? Export it and drag the slider in the Inspector while the game runs. @onready guarantees the child node exists before you grab it — without it, $Sprite2D inside _ready can fail.

    ⚠️ Common Mistake

    Three errors account for most beginner frustration:

    • = assigns, == compares. if health = 100: is wrong. if health == 100: is right.
    • Indentation is syntax in GDScript. Use one consistent style — tabs or four spaces, never mixed.
    • print() writes to the Output panel, not the game screen. To show text to a player you need a Label.

    Input & Simple Movement

    Making things move with the keyboard

    ▼

    Why Godot uses an Input Map

    Naive input code asks "is the D key down?". That seems fine until you want gamepad support, or let players remap keys, or support both WASD and the arrow keys. Godot solves this with an Input Map: you define abstract actions such as move_right, then bind physical keys to them. Your code only ever asks about actions.

    It is a small idea with a large payoff — your code never mentions a specific key again, and supporting a controller later costs you nothing.

    Step 1 — Define the actions

    1. Go to Project → Project Settings → Input Map.
    2. Type move_right in the Action field, click Add.
    3. Click the + beside it and press D. Click + again and press →.
    4. Repeat for move_left (A, ←), move_up (W, ↑), move_down (S, ↓).
    5. Add jump (Space), attack (J), and interact (E).

    Godot already defines ui_accept, ui_cancel and the arrow-key actions. You can build on those, but for a real game you will want your own names.

    Step 2 — The movement script

    movement.gd 
    extends Node2D

@export var speed: float = 300.0

func _process(delta: float) -> void:
    var direction := Vector2.ZERO

    if Input.is_action_pressed("move_right"):
        direction.x += 1
    if Input.is_action_pressed("move_left"):
        direction.x -= 1
    if Input.is_action_pressed("move_up"):
        direction.y -= 1
    if Input.is_action_pressed("move_down"):
        direction.y += 1

    direction = direction.normalized()
    position += direction * speed * delta

    Why normalized()? Because Vector2(1, 1) has length ≈ 1.41. Press right and down together and you travel 41% faster than pressing right alone. Normalising scales every direction to length 1, so speed is always consistent. This is the single most common beginner movement bug in existence.

    The shorter forms — learn them after the long one

    shortcuts.gd 
    # Two axes instead of four checks
var dir := Vector2(
    Input.get_axis("move_left", "move_right"),
    Input.get_axis("move_up", "move_down")
).normalized()

# Or the one-liner — already normalised for you
var dir := Input.get_vector("move_left", "move_right", "move_up", "move_down")

position += dir * speed * delta

    Step 3 — Keep it on screen

    boundaries.gd 
    const SCREEN_W := 1152.0
const SCREEN_H := 648.0

# After movement:
position.x = clamp(position.x, 0.0, SCREEN_W)
position.y = clamp(position.y, 0.0, SCREEN_H)

    clamp(value, min, max) returns min if the value is below it, max if above, otherwise the value unchanged. It is a one-line boundary guard and you will use it constantly.

    How the game scales to the window

    Project Settings → Display → Window → Stretch controls what happens when the window is resized or the game runs on a different screen. Keep preserves your pixel dimensions exactly and letterboxes the edges — the correct choice for pixel art. Expand widens the visible area instead, showing more of the level on a wider screen.

    Two input methods — never confuse them

    MethodReturns trueUse it for
    Input.is_action_pressed()Every frame while heldContinuous movement
    Input.is_action_just_pressed()Only the single frame it was pressedJumping, attacking, dodging

    Using is_action_pressed for a jump makes the player jump sixty times per second while the key is held. Using is_action_just_pressed for movement moves you for exactly one frame and stops. Both bugs are extremely common — now you know to avoid them.

    If/Else & Game Logic

    Making decisions in your game

    ▼

    Conditions are the brain of your game

    Without conditions, a game is a film — identical every time regardless of what the player does. if is what makes your game responsive. It evaluates a condition and runs code only when that condition is true.

    Comparison and logical operators

    If / elif / else and the ternary

    conditions.gd 
    if health <= 0:
    die()
elif health <= 25:
    # critical — flash the health bar red
elif health <= 50:
    # warning — show a low-health icon
else:
    # healthy

# One-line if/else for simple values
var status := "Dead" if health <= 0 else "Alive"

# Combining conditions
if is_on_floor() and Input.is_action_just_pressed("jump"):
    velocity.y = -400

if health <= 0 or lives <= 0:
    game_over()

    elif means "else if". Only the first matching branch runs, then the entire chain is skipped. That ordering matters enormously.

    ⚠️ Common Mistake

    If you write if health < 100: before if health <= 0:, the second branch is unreachable — every value below 100 already matched the first. Put the most extreme condition first. This bug is invisible and maddening.

    Hands-on: a complete health system

    health.gd 
    extends Node2D

var health: int = 100
var max_health: int = 100
var lives: int = 3
var score: int = 0

func take_damage(amount: int) -> void:
    health -= amount
    if health <= 0:
        lives -= 1
        if lives > 0:
            health = max_health   # respawn
        else:
            die()

func heal(amount: int) -> void:
    health += amount
    if health > max_health:
        health = max_health   # never overheal

func add_score(points: int) -> void:
    score += points
    if score >= 300:
        print("Gold rank!")
    elif score >= 200:
        print("Silver rank!")
    elif score >= 100:
        print("Bronze rank!")
    💡 Professor's Tip

    Note the ordering in add_score: gold is checked before silver before bronze. If you reversed it, every score above 100 would print "Bronze". Always test the most demanding condition first.

    Loops & Arrays

    Repeating actions and storing lists

    ▼

    Arrays — ordered lists

    An array is a numbered list. Index 0 is the first item, not the second — this trips up every beginner at least once. Arrays can hold any mix of values, and Godot will enforce a single type if you ask it to.

    arrays.gd 
    var inventory: Array[String] = ["Sword", "Potion"]
var enemy_names: Array[String] = ["Goblin", "Orc", "Dragon"]

# Read and write by index (0-based!)
print(enemy_names[0])       # "Goblin"
enemy_names[1] = "Troll"

# Add, remove, inspect
inventory.push_back("Shield")
inventory.erase("Sword")
print(inventory.size())        # how many items
if enemy_names.has("Dragon"): # contains?
    print("found")
    OperationCode
    Add to endarr.push_back(item)
    Remove matchingarr.erase(item)
    Remove by indexarr.remove_at(i)
    Count itemsarr.size()
    Check containsarr.has(item)
    Clear allarr.clear()
    First / lastarr.front() / arr.back()

    Dictionaries — keyed data

    When several values belong together, a dictionary beats parallel arrays. Instead of keeping enemy_names and enemy_health in sync by hand, store them as one map.

    dictionaries.gd 
    var enemies := {
    "Goblin": 30,
    "Orc": 50,
    "Dragon": 200,
}

print(enemies["Goblin"])       # 30
enemies["Slime"] = 10       # add
enemies.erase("Orc")     # remove
for name in enemies:         # iterate keys
    print(name, " has ", enemies[name], " HP")

    Loops

    loops.gd 
    # Repeat a known number of times
for i in range(5):          # 0,1,2,3,4
    print(i)

for i in range(1, 6):       # 1,2,3,4,5
    print(i)

for i in range(0, 11, 2):  # 0,2,4,6,8,10
    print(i)

# Iterate an array — by index
for i in range(enemy_names.size()):
    print(enemy_names[i])

# Iterate an array — directly (cleaner)
for name in enemy_names:
    print(name)

# Repeat while a condition holds
var count := 0
while count < 10:
    count += 1   # forget this = infinite loop

# Control flow inside a loop
for i in range(100):
    if i == 5: break       # exit the loop
    if i % 2 == 0: continue  # skip this iteration

    Hands-on: an enemy manager

    enemy_manager.gd 
    extends Node2D

var enemies := [
    {"name": "Goblin", "hp": 30,  "alive": true},
    {"name": "Orc",   "hp": 50,  "alive": true},
    {"name": "Dragon","hp": 200, "alive": true},
]

func _ready() -> void:
    display_all()
    defeat("Orc")
    print("---")
    display_all()

func display_all() -> void:
    for e in enemies:
        var status := "DEAD" if not e["alive"] else "alive"
        print(e["name"], ": ", e["hp"], " HP (", status, ")")

func defeat(name: String) -> void:
    for e in enemies:
        if e["name"] == name:
            e["alive"] = false
            e["hp"] = 0

func count_alive() -> int:
    var n := 0
    for e in enemies:
        if e["alive"]: n += 1
    return n
    💡 Professor's Tip

    An array of dictionaries is the single most useful data shape in a small game. It keeps related values together, reads clearly, and survives being saved to disk. Reach for it before you reach for anything more complicated.

    Signals — Nodes Talking to Each Other

    Decoupled communication between game objects

    ▼

    What signals solve

    Signals are Godot's implementation of the Observer pattern. One node announces that something happened; any number of other nodes listen and react. Crucially, the announcer does not need to know who is listening, and the listeners do not need to know who is announcing.

    Why does that matter? Because it keeps your code decoupled. Your player script should not hold a reference to your health bar, and your health bar should not hold a reference to your player. Instead: the player emits health_changed, and anything that cares connects to it. You can later add a damage-number popup and a hurt sound — both listening to the same signal — without touching the player script at all.

    This is the architectural habit that separates a tangled prototype from a game you can still work on in three months.

    Declaring and emitting

    player.gd 
    extends CharacterBody2D

# Declare custom signals at the top of the script
signal health_changed(new_health: int, max_health: int)
signal died
signal coin_collected(value: int)

var health: int = 100
var max_health: int = 100

func take_damage(amount: int) -> void:
    health -= amount
    if health <= 0:
        health = 0
        health_changed.emit(health, max_health)
        died.emit()
    else:
        health_changed.emit(health, max_health)

    Connecting in code

    ui.gd 
    extends CanvasLayer

@onready var bar: TextureProgressBar = $HealthBar

func _ready() -> void:
    var player := get_tree().get_first_node_in_group("player")
    if player:
        player.health_changed.connect(_on_health_changed)
        player.died.connect(_on_player_died)

func _on_health_changed(new_health: int, max_health: int) -> void:
    bar.value = float(new_health) / float(max_health) * 100.0

func _on_player_died() -> void:
    $GameOver.visible = true

    Notice that the UI script never mentions damage logic. It only cares about the signal. That is the whole point.

    Connecting in the editor

    You do not have to connect in code. Select a node, open the Node dock (right panel, next to Inspector), switch to the Signals tab, double-click a signal, pick the receiving node, and type the method name. Godot writes the connection into the scene file.

    Both approaches are valid. Use the editor for simple UI wiring, and code when the connection must be dynamic — for example connecting to an enemy you just spawned at runtime.

    CharacterBody2D & Physics

    The correct way to move a character

    ▼

    Why not just set position?

    On Day 4 you moved a node by writing position += dir * speed * delta. That works for a bouncing logo. It fails completely for a game character, because nothing stops the sprite walking through a wall and nothing makes it fall when it walks off a ledge.

    CharacterBody2D is Godot's purpose-built node for characters. Instead of setting position directly, you set velocity — a vector describing how fast and in what direction the body wants to move — and then call move_and_slide(). The physics engine moves the body, resolves collisions, and stops it at walls.

    The mental model: you request movement, the engine grants what it can.

    The standard movement loop

    player.gd 
    extends CharacterBody2D

@export var speed: float = 300.0
@export var jump_velocity: float = -400.0
@export var gravity: float = 980.0

func _physics_process(delta: float) -> void:
    # 1. Gravity — pulls down unless grounded
    if not is_on_floor():
        velocity.y += gravity * delta

    # 2. Jump — grounded, and a FRESH press
    if Input.is_action_just_pressed("jump") and is_on_floor():
        velocity.y = jump_velocity

    # 3. Horizontal input
    velocity.x = Input.get_axis("move_left", "move_right") * speed

    # 4. Let physics resolve collisions
    move_and_slide()

    Everything that touches velocity lives in _physics_process, never _process. Physics runs at a fixed rate, so your character behaves identically whether the game runs at 30 or 144 frames per second.

    Making it feel good — coyote time and jump buffering

    A platformer that "works" and one that "feels great" differ by two small techniques. Both exist because players are not frame-perfect.

    Coyote time allows a jump for about 100 ms after walking off a ledge. Players press jump a fraction late constantly; without this, the jump feels broken and they blame the game.

    Jump buffering remembers a jump press for about 100 ms before landing. Players press jump just before touching the ground; without this, the input vanishes and the jump feels ignored.

    feel.gd 
    extends CharacterBody2D

@export var speed: float = 300.0
@export var jump_velocity: float = -400.0
@export var gravity: float = 980.0

const COYOTE_TIME := 0.1
const BUFFER_TIME := 0.1

var coyote_timer: float = 0.0
var buffer_timer: float = 0.0

func _physics_process(delta: float) -> void:
    if not is_on_floor():
        velocity.y += gravity * delta

    # Coyote: refresh while grounded, drain while airborne
    if is_on_floor():
        coyote_timer = COYOTE_TIME
    else:
        coyote_timer -= delta

    # Buffer: record a press, drain over time
    if Input.is_action_just_pressed("jump"):
        buffer_timer = BUFFER_TIME
    else:
        buffer_timer -= delta

    # Jump only when both timers are still live
    if buffer_timer > 0.0 and coyote_timer > 0.0:
        velocity.y = jump_velocity
        buffer_timer = 0.0
        coyote_timer = 0.0

    velocity.x = Input.get_axis("move_left", "move_right") * speed
    move_and_slide()
    ⚠️ Common Mistake

    is_on_floor() is only meaningful after move_and_slide() has run. Checking it at the very top of _physics_process returns last frame's answer, producing an off-by-one error that is genuinely hard to spot. The pattern above works because the previous frame's collision state is exactly what coyote time needs.

    Collisions & Layers

    Who collides with whom, and how to detect it

    ▼

    The layer and mask system

    Every physics body carries two numbers: collision_layer (which layers it sits on) and collision_mask (which layers it detects). Godot compares them as bitmasks.

    A collision occurs when (A.layer & B.mask) != 0 or (B.layer & A.mask) != 0. In plain language: "am I on a layer they care about, or are they on a layer I care about?" If neither is true, they pass right through each other — silently, with no error message.

    This is why a player sometimes falls through a floor for no apparent reason: the mask simply does not include the floor's layer. Learning to read layers is learning to debug physics.

    Setting up layers

    1. Go to Project → Project Settings → Layer Names → 2D Physics.
    2. Name the layers: 1 Player, 2 Enemy, 3 World, 4 Pickup, 5 Hazard, 6 Projectile.
    3. Select each node and set Collision → Layer and Mask in the Inspector.
    NodeLayer (is on)Mask (detects)
    PlayerPlayerEnemy · World · Pickup · Hazard · Projectile
    EnemyEnemyPlayer · World · Projectile
    Wall / floorWorldPlayer · Enemy · Projectile
    CoinPickupPlayer
    SpikesHazardPlayer
    Player bulletProjectileEnemy · World

    Notice that coins detect only the player, while the player also detects coins. Neither needs to be on the other's layer. That asymmetry is normal and intentional.

    Reading collisions on a CharacterBody2D

    collision_read.gd 
    func _physics_process(delta: float) -> void:
    # ... movement ...
    move_and_slide()

    # Inspect what we hit this frame
    for i in get_slide_collision_count():
        var col := get_slide_collision(i)
        var other := col.get_collider()
        if other and other.is_in_group("hazard"):
            take_damage(10)

    Hands-on: a collision sandbox

    1. Player — layer Player, mask Enemy+World+Pickup+Hazard.
    2. Walls — layer World, mask Player+Enemy.
    3. Coin — layer Pickup, mask Player.
    4. Spikes — layer Hazard, mask Player.
    5. Enemy — layer Enemy, mask Player+World.

    Expected results: the player is stopped by walls and enemies; passes through the coin but detects it; takes damage on the spikes; the enemy is blocked by walls but ignores both coins and spikes. If any of those fail, the mask is wrong — not the shapes.

    ⚠️ Common Mistake

    Four Godot 4.7 quirks worth knowing now, because each one fails silently:

    • CanvasModulate tints everything on the canvas. For per-item colour changes use self_modulate instead.
    • draw_line() is no longer antialiased in 4.x — increase width to compensate.
    • AudioStreamPlayer.area_mask defaults to 0 in 4.7, so reverb zones quietly stop working. Set it explicitly.
    • Light2D requires matching range_item_cull_mask and the target's light_mask — a mismatch produces no light and no error.

    Area2D & Triggers

    Sensors for pickups, zones and hazards

    ▼

    The sensor node

    Area2D is a physics node that detects overlaps but never physically blocks. Two bodies pass straight through each other; the area simply reports that they overlapped. Think of it as a tripwire or a motion sensor.

    Use it for anything that should be touched rather than bumped: coins, keys, doors, checkpoints, ladders, damage zones, spawn triggers, dialogue ranges, finish lines.

    Building a coin

    coin.gd 
    extends Area2D

@export var value: int = 10

func _ready() -> void:
    # Built-in signal: a physics body entered
    body_entered.connect(_on_body_entered)

func _on_body_entered(body: Node2D) -> void:
    if body.is_in_group("player"):
        body.add_score(value)
        queue_free()   # remove the coin safely

    queue_free() is the correct way to delete a node. It marks the node for deletion at the end of the frame, after all signals have been delivered. Calling free() immediately can crash the engine mid-signal — this is a real crash, not a theoretical one.

    Building a damage zone

    hazard.gd 
    extends Area2D

@export var damage: int = 10

func _ready() -> void:
    body_entered.connect(_on_body_entered)

func _on_body_entered(body: Node2D) -> void:
    if body.is_in_group("player"):
        body.take_damage(damage)

    Groups — the organising principle

    Groups are labels you assign to nodes, and they are the most flexible tool in Godot for organising a game.

    groups.gd 
    func _ready() -> void:
    add_to_group("player")
    add_to_group("damageable")

if body.is_in_group("player"):
    print("that is the player")

if is_in_group("enemies"):
    queue_free()   # a "kill all enemies" bomb

var pickups := get_tree().get_nodes_in_group("pickups")
for p in pickups:
    p.collected()

    Assign groups in the editor (Node dock → Groups tab) or in _ready(). Group queries are cached, so even hundreds of nodes are cheap to query.

    Monitoring vs monitorable

    PropertyEffect
    monitoringIf false, this area stops detecting others
    monitorableIf false, other areas cannot detect this one

    Set monitoring = false on a hazard that is currently inactive. It costs nothing and it cannot fire.

    Camera2D & Viewport

    Following the player and reading coordinates

    ▼

    What the camera does

    The camera decides which rectangular slice of your game world is drawn to the screen. Without one you see the world from the origin — usually the top-left corner. In a real game the camera follows the player and stops at the edges of the level.

    Setting it up

    camera.gd 
    extends Camera2D

func _ready() -> void:
    make_current()                       # activate this camera
    position_smoothing_enabled = true      # lag behind — feels better
    position_smoothing_speed = 5.0

    # Stop the camera showing beyond the level edges
    limit_left = 0
    limit_top = 0
    limit_right = 3840
    limit_bottom = 2160

    zoom = Vector2(2, 2)             # 2 = zoomed in twice

    Parent the camera to the player and it follows automatically. The smoothing makes the follow feel weighty rather than rigid — a tiny change with a large effect on how the game feels.

    Screen shake

    shake.gd 
    func shake(intensity: float, duration: float) -> void:
    var tween := create_tween()
    var steps := 6
    for i in range(steps):
        tween.tween_property(self, "offset",
            Vector2(randf_range(-intensity, intensity),
                      randf_range(-intensity, intensity)),
            duration / steps)
    # settle back to centre
    tween.tween_property(self, "offset", Vector2.ZERO, duration / steps)

    Call shake(8.0, 0.3) on a hit or an explosion. Short, sharp, and over before it becomes annoying — that is the entire craft of screen shake.

    Reading the mouse in world space

    mouse.gd 
    func _process(delta: float) -> void:
    # Mouse position in WORLD coordinates,
    # already accounting for camera position and zoom
    var mouse_world := get_global_mouse_position()
    look_at(mouse_world)   # face the cursor

    Camera lookahead

    A subtle trick that makes platformers feel noticeably better: shift the camera slightly in the direction the player is moving so they can see further ahead.

    lookahead.gd 
    func _physics_process(delta: float) -> void:
    # ... movement ...
    move_and_slide()

    var target := Vector2(velocity.x * 0.15, velocity.y * 0.05)
    target = target.limit_length(60.0)
    $Camera2D.offset = $Camera2D.offset.lerp(target, 5.0 * delta)

    extends CharacterBody2D

    UI System — Control Nodes & Layout

    Building the interface of your game

    ▼

    Everything UI is a Control

    Every visual element in Godot's interface — buttons, labels, bars, panels — derives from a single base class: Control. If a node draws to the screen in a UI context, it is a Control. That single inheritance chain is what makes the UI system coherent: anchors, sizing and focus behaviour work the same way everywhere.

    UI nodes live inside a CanvasLayer, which draws on its own layer above the game world. That is exactly why your health bar stays put while the camera moves — it is not in the world, it is on a layer that ignores the camera entirely.

    Content nodes vs layout containers

    KindNodesIts job
    ContentLabel, Button, LineEdit, TextureRect, TextureProgressBarDisplay something
    ContainerHBoxContainer, VBoxContainer, MarginContainer, GridContainer, CenterContainer, PanelContainerArrange their children automatically

    Containers solve a problem every beginner hits: UI that breaks when the window resizes. If you place a Label at pixel (20, 20), it stays there forever, even if the window doubles in size. If you place it inside a MarginContainer anchored to the top-left, it stays 20 pixels from the corner at any resolution.

    Anchors and size flags

    Anchors define which part of the parent a Control sticks to. Anchor to the top-left corner and it follows that corner. Anchor to the full rect and it stretches with its parent. Combined with size flags (fill, expand, shrink centre), this gives you responsive layouts without writing a single line of code.

    HUD, Score & Autoloads

    Global state that survives scene changes

    ▼

    The problem autoloads solve

    When you change scenes, everything in the old scene is destroyed. That is usually what you want — a fresh level, no leftover enemies. But it is a disaster for anything that should persist: the player's score, their inventory, the chosen difficulty, the audio volume.

    Autoloads (also called singletons) are nodes Godot loads at startup and never destroys, regardless of which scene is running. They sit in the root of the scene tree, permanently available.

    Creating a GameManager

    1. Create a script game_manager.gd extending Node.
    2. Go to Project → Project Settings → Autoload.
    3. Add the script and give it the name GameManager.
    4. Access it from anywhere as GameManager.
    game_manager.gd 
    extends Node

signal score_changed(new_score: int)
signal health_changed(new_health: int)

var score: int = 0
var health: int = 100
var max_health: int = 100
var level: int = 1

func add_score(points: int) -> void:
    score += points
    score_changed.emit(score)

func take_damage(amount: int) -> void:
    health -= amount
    if health < 0: health = 0
    health_changed.emit(health)
    if health == 0:
        game_over()

func reset_game() -> void:
    score = 0
    health = max_health
    level = 1
    score_changed.emit(score)
    health_changed.emit(health)

    Notice the signals again. The GameManager does not know a HUD exists. It announces that the score changed, and anything listening updates itself. That is Day 8's decoupling applied at the global level.

    The HUD listens

    hud.gd 
    extends CanvasLayer

@onready var health_bar: TextureProgressBar = $Margin/HBox/HealthBar
@onready var score_label: Label = $Margin/HBox/ScoreLabel

func _ready() -> void:
    GameManager.score_changed.connect(_on_score_changed)
    GameManager.health_changed.connect(_on_health_changed)
    refresh()

func _on_score_changed(new_score: int) -> void:
    score_label.text = "Score: %d" % new_score

func _on_health_changed(new_health: int) -> void:
    health_bar.value = float(new_health) / float(GameManager.max_health) * 100.0

func refresh() -> void:
    _on_score_changed(GameManager.score)
    _on_health_changed(GameManager.health)

    formatting.gd

print("Score: %d" % score)          # Score: 42

    TileMapLayer & TileSet

    Building levels efficiently

    ▼

    Why tilemaps beat sprites

    You could build a level by placing three hundred Sprite2D nodes. It would work, and it would be slow, unwieldy and impossible to edit. A TileMapLayer stores a grid of tile indices instead of individual nodes. Three hundred tiles become three hundred integers — cheap to store, cheap to draw, and the engine batches them into a handful of draw calls.

    Tilemaps also give you collision, occlusion and navigation per tile, plus a paint interface that makes level design feel like using an image editor rather than a node tree.

    TileSet vs TileMapLayer

    ResourceWhat it is
    TileSetThe palette — textures, collision shapes, navigation polygons, custom data
    TileMapLayerThe canvas — the grid of tile indices you paint

    You can share one TileSet across many TileMapLayers, and even across many levels. That is the intended workflow: build your palette once, then paint every level with it.

    Setting up a tileset

    1. Add a TileMapLayer node to your level.
    2. In the Inspector, Tile Set → New TileSet.
    3. Click the TileSet to open the TileSet editor at the bottom.
    4. Click + → New Atlas Sources and load your tileset image.
    5. Set the Tile size — 16×16 or 32×32 are standard.
    6. Click tiles in the atlas to select them, then paint in the viewport.
    7. For solid tiles, add a Physics Layer and draw a collision shape on the tile.

    Reading tiles from code

    tile_read.gd 
    @onready var tilemap: TileMapLayer = $TileMapLayer

func _physics_process(delta: float) -> void:
    # Which tile is under the player right now?
    var coord := tilemap.local_to_map(tilemap.to_local(global_position))
    var source_id := tilemap.get_cell_source_id(coord)

    if source_id == -1:
        return   # empty cell

    # Read custom data attached in the TileSet editor
    var data := tilemap.get_cell_tile_data(coord)
    if data:
        var damage := data.get_custom_data("damage") or 0
        var climbable := data.get_custom_data("climbable") != null
        if damage > 0:
            take_damage(damage)

    Multiple layers

    Use several TileMapLayer nodes for separation rather than one giant layer. This is cleaner and lets you toggle rendering per layer.

    level.tscn structure 
    Level (Node2D)
├── Background   (TileMapLayer — no collision, drawn behind)
├── Terrain      (TileMapLayer — collision enabled)
├── Foreground   (TileMapLayer — drawn over the player)
├── Player       (instanced player.tscn)
└── Camera2D

    Scene Management & Flow

    Moving between scenes and managing state

    ▼

    The scene lifecycle

    When Godot changes scenes it frees the current scene's nodes and instantiates the new one. That is clean and predictable — and it means anything you stored on a node vanishes. Global state lives in autoloads; everything else is rebuilt fresh.

    Because freeing happens at a specific point in the frame, you must never change scenes during a signal callback or a physics step. Use call_deferred, or change from a place where the tree is idle.

    A SceneManager autoload

    scene_manager.gd 
    extends Node

func change_scene(path: String) -> void:
    # deferred so we never free a node mid-signal
    call_deferred("_deferred_change", path)

func _deferred_change(path: String) -> void:
    get_tree().change_scene_to_file(path)

func reload_scene() -> void:
    get_tree().reload_current_scene()

func quit_game() -> void:
    get_tree().quit()

    change_scene_to_file() is the Godot 4.x method. The old change_scene() is gone — using it produces an error. If you see that error in a tutorial, the tutorial predates Godot 4 and you should find another one.

    Instancing scenes at runtime

    spawning.gd 
    extends Node2D

@export var enemy_scene: PackedScene
@export var spawn_interval: float = 2.0

func _ready() -> void:
    $SpawnTimer.timeout.connect(_on_spawn)
    $SpawnTimer.wait_time = spawn_interval
    $SpawnTimer.start()

func _on_spawn() -> void:
    var enemy := enemy_scene.instantiate()   # create the node
    enemy.global_position = _random_edge_position()
    add_child(enemy)                       # must be added to run

    instantiate() creates the node. It does nothing until you add_child() it into the scene tree — without that, no _ready() runs and no signals connect. This is the single most common runtime-instancing mistake.

    GPU vs CPU particles

    NodeRuns onUse when
    GPUParticles2DGraphics cardAlways, unless targeting very weak hardware
    CPUParticles2DCPUOld devices, or when you need per-particle code

    GPUParticles2D handles thousands of particles at 60 FPS because the work happens on the GPU. It requires a ParticleProcessMaterial resource, which defines how particles are emitted, how they move, and how they look.

    Setting up a particle effect

    1. Add a GPUParticles2D node.
    2. In the Inspector, Process Material → New ParticleProcessMaterial.
    3. Set the Emission Shape — point, sphere, box.
    4. Set Direction and Spread to control where particles fly.
    5. Set Gravity — (0, 980) for falling dust, (0, −200) for rising smoke.
    6. Set Initial Velocity, Scale, Color and Lifetime.
    7. Optionally assign a texture to the material.

    Dust while running

    A one-shot explosion

    explosion.gd 
    func explode(pos: Vector2) -> void:
    var fx := GPUParticles2D.new()
    fx.one_shot = true          # emit once, then stop
    fx.explosiveness = 1.0      # all particles at once
    fx.amount = 24
    fx.lifetime = 0.8
    fx.global_position = pos
    add_child(fx)
    fx.emitting = true

    # clean up after the particles have lived
    var timer := get_tree().create_timer(1.5)
    timer.timeout.connect(fx.queue_free)

    Hitstop and flash

    juice.gd 
    func hitstop(duration: float = 0.05) -> void:
    Engine.time_scale = 0.0
    await get_tree().create_timer(duration).timeout
    Engine.time_scale = 1.0

func flash_white(sprite: CanvasItem) -> void:
    sprite.self_modulate = Color(4.0, 4.0, 4.0)  # overbright
    var tween := create_tween()
    tween.tween_property(sprite, "self_modulate", Color.WHITE, 0.15)

    Engine.time_scale slows the entire simulation. A 50 ms freeze on a heavy impact reads as weight and power — it is one of the cheapest and most effective juice techniques in games.

    The juice checklist

    When a mechanic feels flat, add from this list in order of impact:

    • Screen shake — the highest impact per line of code.
    • Particles — dust, sparks, impact bursts.
    • Hitstop — a few frames of freeze on a heavy hit.
    • Flash — the hit object goes white for a frame.
    • Sound — a punchy SFX with slight pitch variation.
    • Squash and stretch — scale the sprite briefly on landing.
    • Camera nudge — a small push in the impact direction.
    ⚠️ Common Mistake

    Engine.time_scale is global. If you set it to 0 and forget to set it back to 1.0, your game stays frozen forever and it will look like a crash. Always restore it — and if the game can be paused mid-hitstop, restore it on unpause too.

    Tween — Smooth Animations

    Animating any property without manual math

    ▼

    Why tweens exist

    You could animate a door opening by writing position.x += 2.0 every frame and stopping at a target. That works, but it is tedious, and it makes the animation speed depend on frame rate. A Tween interpolates a property from its current value to a target value over a duration, handling the timing and easing for you.

    Tweens are the right tool for one-off movements: UI transitions, doors, camera pans, health bar drains, damage popups, cutscene beats.

    The basics

    tween_basics.gd 
    func open_door() -> void:
    var tween := create_tween()
    tween.tween_property($Door, "position:x", 200.0, 0.4)
    tween.parallel().tween_property($Door, "modulate:a", 0.0, 0.4)

func fade_and_free(node: CanvasItem) -> void:
    var tween := create_tween()
    tween.tween_property(node, "modulate:a", 0.0, 0.5)
    tween.tween_callback(node.queue_free)

func pulse() -> void:
    var tween := create_tween().set_loops(3)
    tween.tween_property(self, "scale", Vector2(1.2, 1.2), 0.15)
    tween.tween_property(self, "scale", Vector2.ONE, 0.15)

    Easing and transitions

    easing.gd 
    var tween := create_tween()
tween.tween_property(self, "position:y", 300.0, 0.6)
    .set_ease(Tween.EASE_OUT)
    .set_trans(Tween.TRANS_BOUNCE)

    EASE_OUT decelerates into the destination — good for UI. TRANS_BOUNCE overshoots and settles — good for playful elements. TRANS_SINE with EASE_IN_OUT is the neutral default for most motion.

    The motion is triggered at runtimeThe motion is authored and reused
    It is short and one-offIt is a multi-track sequence
    You need code-driven controlYou want to preview it in the editor

    State Machines

    Managing complex behaviour cleanly

    ▼

    The problem a state machine solves

    A player character can be idle, walking, jumping, falling, attacking, hurt, climbing or dead. Written as nested if statements, that becomes a tangle where adding one state breaks three others.

    A state machine makes it explicit: the character is in exactly one state at a time, and each state defines what it does and what it is allowed to become.

    Enums and match

    state_machine.gd 
    extends CharacterBody2D

enum State { IDLE, WALK, JUMP, FALL, ATTACK, HURT, DEAD }

var state: State = State.IDLE

func _physics_process(delta: float) -> void:
    _update_state()
    _run_state(delta)
    move_and_slide()

# WHICH state are we in?
func _update_state() -> void:
    match state:
        State.IDLE:
            if not is_on_floor(): state = State.FALL
            elif Input.is_action_just_pressed("attack"): state = State.ATTACK
            elif velocity.x != 0.0: state = State.WALK
        State.WALK:
            if not is_on_floor(): state = State.FALL
            elif velocity.x == 0.0: state = State.IDLE
        State.JUMP:
            if velocity.y > 0.0: state = State.FALL
        State.FALL:
            if is_on_floor(): state = State.IDLE
        State.ATTACK, State.HURT, State.DEAD:
            pass   # their own timers handle the exit

# WHAT does this state do?
func _run_state(delta: float) -> void:
    match state:
        State.IDLE:
            velocity.x = 0.0
            $AnimatedSprite2D.play("idle")
        State.WALK:
            velocity.x = Input.get_axis("move_left", "move_right") * speed
            $AnimatedSprite2D.play("walk")
        State.JUMP, State.FALL:
            velocity.y += GRAVITY * delta
            $AnimatedSprite2D.play("jump")
        State.ATTACK:
            velocity.x = 0.0
            $AnimatedSprite2D.play("attack")
        State.HURT, State.DEAD:
            velocity.x = 0.0

    Splitting _update_state (transitions) from _run_state (behaviour) is what keeps this readable. You can glance at the first function and see every way the character can change state — which is exactly the question you ask when a bug appears.

    💡 Professor's Tip

    State machines scale; nested if-statements do not. The moment you find yourself writing a third level of indentation inside _physics_process, stop and convert to a state machine. You will save yourself hours.

    Save & Load System

    Persisting progress between sessions

    ▼

    Where saves live

    Godot writes saves to user://, which maps to a platform-specific folder — on Windows, %APPDATA%/Godot/app_userdata/YourGame/. Never write to res://: that is the read-only project directory, and in an exported game it is packed inside the executable.

    Writing a save

    save.gd 
    const SAVE_PATH := "user://savegame.json"

func save_game() -> void:
    var data := {
        "score": GameManager.score,
        "health": GameManager.health,
        "level": GameManager.level,
        "position": [global_position.x, global_position.y],
        "unlocked": GameManager.unlocked_levels,
    }

    var file := FileAccess.open(SAVE_PATH, FileAccess.WRITE)
    if file == null:
        printerr("Could not open save file")
        return
    file.store_string(JSON.stringify(data, "  "))
    file.close()
    print("Game saved")

    Reading a save

    load.gd 
    func load_game() -> bool:
    if not FileAccess.file_exists(SAVE_PATH):
        return false

    var file := FileAccess.open(SAVE_PATH, FileAccess.READ)
    var text := file.get_as_text()
    file.close()

    var parsed = JSON.parse_string(text)
    if not parsed is Dictionary:
        printerr("Save file is corrupted")
        return false

    GameManager.score = parsed.get("score", 0)
    GameManager.health = parsed.get("health", 100)
    GameManager.level = parsed.get("level", 1)
    return true

    parsed.get("key", default) is essential. A save written by an older version of your game will lack new keys — get with a default prevents a crash the first time a player updates.

    ⚠️ Common Mistake

    JSON.stringify() cannot serialise Resources or Nodes. Save paths and IDs as strings, then reload the resources at runtime. Never store a live node reference in a save — that node no longer exists next session, and loading it will crash.

    Enemy AI Basics

    Making enemies that feel intentional

    ▼

    AI is just rules

    Game AI is not intelligence — it is a set of rules that produce behaviour the player reads as deliberate. A patroller that turns at walls looks smart because the player expects walls to matter. A chaser that gives up when the player escapes looks smart because the player expects pursuit to have limits.

    The craft is in choosing rules that are legible: the player should be able to predict what the enemy will do next. An unpredictable enemy does not feel intelligent; it feels broken.

    RayCast2D — line of sight

    raycast.gd 
    @onready var ray: RayCast2D = $RayCast2D

func _ready() -> void:
    ray.enabled = true

func has_line_of_sight(target: Node2D) -> bool:
    ray.target_position = ray.to_local(target.global_position)
    ray.force_raycast_update()
    if ray.is_colliding():
        return ray.get_collider() == target
    return true

    A RayCast2D casts a line and reports what it hits. Set its collision mask to the World layer only, and it detects walls while ignoring other enemies.

    A three-state chaser

    ai_chaser.gd 
    extends CharacterBody2D

enum AI { IDLE, CHASE, RETURN }

@export var speed: float = 140.0
var ai_state: AI = AI.IDLE
var player: Node2D = null
var home: Vector2

func _ready() -> void:
    home = global_position
    $DetectionZone.body_entered.connect(func(b):
        if b.is_in_group("player"): player = b)
    $DetectionZone.body_exited.connect(func(b):
        if b == player: player = null)

func _physics_process(delta: float) -> void:
    match ai_state:
        AI.IDLE:
            velocity.x = 0.0
            if player: ai_state = AI.CHASE
        AI.CHASE:
            if not player or not has_line_of_sight(player):
                ai_state = AI.RETURN
            else:
                velocity.x = sign(player.global_position.x - global_position.x) * speed
        AI.RETURN:
            var to_home := home - global_position
            if to_home.length() < 8.0:
                velocity.x = 0.0
                ai_state = AI.IDLE
            else:
                velocity.x = sign(to_home.x) * speed * 0.7
    velocity.y += 980.0 * delta
    move_and_slide()
    $AnimatedSprite2D.flip_h = velocity.x < 0.0

    The RETURN state is what makes this feel designed rather than broken. An enemy that chases forever feels like a bug; one that gives up and walks home feels like a creature.

    Difficulty through numbers

    You do not need new behaviours to change difficulty. A patrol speed of 120 with a two-second wind-up reads as easy; 260 with a 0.3-second wind-up reads as brutal. Tune numbers before writing new AI — it is faster, safer, and easier to reverse.

    Design the data before the code

    A dialogue system is mostly data. The code is a small state machine that walks through lines; the content is an array of dictionaries. Getting the data shape right is 80% of the work.

    The dialogue box

    dialogue.gd 
    extends CanvasLayer

signal dialogue_finished

@onready var speaker_label: Label = $Panel/Speaker
@onready var text_label: Label = $Panel/Text

var lines: Array[Dictionary] = []
var index: int = 0
var typing := false
var full_text := ""

func start(data: Array[Dictionary]) -> void:
    lines = data
    index = 0
    $Panel.visible = true
    get_tree().paused = true
    show_line()

func show_line() -> void:
    var line: Dictionary = lines[index]
    speaker_label.text = line["speaker"]
    full_text = line["text"]
    text_label.text = ""
    typing = true
    for i in range(full_text.length()):
        if not typing: break   # player skipped
        text_label.text += full_text[i]
        await get_tree().create_timer(0.025).timeout
    typing = false

func _unhandled_input(event: InputEvent) -> void:
    if not event.is_action_pressed("interact"): return
    if typing:
        typing = false          # skip to the full text
        return
    index += 1
    if index >= lines.size():
        end_dialogue()
    else:
        show_line()

func end_dialogue() -> void:
    $Panel.visible = false
    get_tree().paused = false
    dialogue_finished.emit()

    The structure around your game

    ▼

    Why flow matters

    A game is more than its levels. The menu is the first thing a player sees; the pause screen is where they adjust settings; the game-over screen is where you ask them to try again. Sloppy flow makes a good game feel amateur.

    Map your flow before building it. Every arrow in that diagram is a scene change you must implement and test.

    A menu scene

    menu.gd 
    extends Control

        SceneManager.change_scene("res://scenes/level_1.tscn")

    $SettingsPanel.visible = not $SettingsPanel.visible

func _on_quit_pressed() -> void:
    get_tree().quit()

    Call grab_focus() on the default button so a player can navigate the menu with a gamepad or the arrow keys without touching the mouse.

    Scene transitions

    transition.gd 
    extends CanvasLayer

@onready var fade: ColorRect = $Fade

func _ready() -> void:
    fade_to(0.0, 0.4)   # fade in on load

func fade_to(target_alpha: float, duration: float) -> void:
    var tween := create_tween()
    tween.tween_property(fade, "modulate:a", target_alpha, duration)

func transition_to(path: String) -> void:
    fade_to(1.0, 0.3)
    await create_timer(0.3).timeout
    SceneManager.change_scene(path)

    Put this layer in every scene, or better, in a shared base scene. Fade out, change, fade in — three lines that make transitions feel professional and hide the load.

    A level-select screen is just a grid of buttons, each disabled if the level is not yet unlocked. Read the unlocked list from your save file, then enable or grey out each button accordingly. It gives the player a sense of progress and costs you almost nothing to build.

    Polish & Game Feel

    The difference between works and feels good

    ▼

    Polish is not decoration

    Polish is the work that makes mechanics feel intentional. A jump with no feedback feels broken even when it is correct. A jump with a squash, a dust puff, a sound and a one-frame landing pause feels good — and the player cannot always say why.

    Invincibility frames

    iframes.gd 
    var is_invincible := false

func take_damage(amount: int) -> void:
    if is_invincible: return
    health -= amount
    is_invincible = true

    # blink so the player can SEE the state
    var tween := create_tween().set_loops(6)
    tween.tween_property(sprite, "modulate:a", 0.3, 0.06)
    tween.tween_property(sprite, "modulate:a", 1.0, 0.06)

    await get_tree().create_timer(0.75).timeout
    is_invincible = false

    The blink is not cosmetic — it communicates the state. A player who understands they are temporarily invincible will use it deliberately, which turns a defensive mechanic into a tactical one.

    Combo system

    combo.gd 
    var combo := 0
var combo_timer: float = 0.0

func _process(delta: float) -> void:
    if combo_timer > 0.0:
        combo_timer -= delta
        if combo_timer <= 0.0:
            combo = 0   # combo expired

func register_hit() -> void:
    combo += 1
    combo_timer = 2.0
    var bonus := combo * 5
    GameManager.add_score(bonus)
    $ComboLabel.text = "x%d" % combo
    $ComboLabel.visible = combo > 1

    Difficulty balancing

    Balance by changing numbers, not by adding exceptions. Concrete levers, in order of usefulness:

    • Enemy speed — the single biggest difficulty dial.
    • Health and damage values — how many hits to kill, how many to die.
    • Spawn rate — pressure over time.
    • Attack wind-up — longer telegraphs are easier to read.
    • Checkpoint spacing — the real difficulty of a platformer.
    • Resource scarcity — health pickups, ammo, currency.

    Playtesting rules

    • Watch someone play without helping them. Your explanations invalidate the test.
    • Note where they hesitate — hesitation is a design failure, not a player failure.
    • Ask "what did you expect to happen?" rather than "did you like it?"
    • Test on the worst hardware you intend to support.
    • Play for longer than feels necessary. Fatigue reveals balance problems.

    Final Project — Design Your Game

    Plan before you build

    ▼

    Write the design first

    Twenty minutes of design saves twenty hours of rebuilding. Write these four things before you open Godot:

    1. The concept — one paragraph. What is the game, and why is it interesting?
    2. Three mechanics — no more. What does the player actually do?
    3. The hook — what makes the first thirty seconds compelling?
    4. The smallest shippable version — one level, one enemy, one goal. That is the target. Everything else is stretch.
    ⚠️ Common Mistake

    Every beginner designs a game they cannot finish. The professional move is to design something you can finish in a week, then cut it in half. A finished small game is a portfolio piece; an unfinished large game is nothing at all.

    Five concepts you can actually finish

    ConceptCore skill it teaches
    A room-based puzzle platformerTilemaps, triggers, state machines
    A top-down collectathonGrid movement, inventory, save and load
    A wave-survival arenaSpawning, difficulty curves, combos
    A dialogue-driven mysteryDialogue system, flags, scene flow
    A precision platformerFeel, coyote time, checkpoints

    Design the player character

    Sketch it — even badly. You need to know four things:

    • How tall is it? This sets your tile size and collision box.
    • What is its silhouette? It must be readable at a glance.
    • What is its one distinctive feature — the thing the player remembers?
    • What animations does it need? Idle, walk and jump is the minimum.

    Design one level on paper

    Before touching the tilemap, sketch the level:

    • Where does the player start, and what do they see first?
    • What is the critical path — the route they must take?
    • Where are the optional branches, and what reward does each hold?
    • Where does it end, and what tells the player they have finished?

    A level is a sequence of reasons to be there. If a room has no reason to exist, merge it into a neighbour. This is the same principle that separates a good level from a procedurally generated one.

    Write your design down somewhere you will not lose it. You will otherwise redesign the game halfway through, and a half-built game with a changed design is the most common way beginner projects die.

    What a Game Actually Is

    Systems, rules, and the loop that makes it a game

    ▼

    Systems, not stories

    Most beginners describe a game by its story or its setting: "it's about a space marine." That is not a game. A game is a set of systems — rules that interact — and the player's job is to learn them.

    A system is anything that takes an input, applies a rule, and produces an output. Jump: press a button, the character rises. Enemy: touches you, you lose health. Economy: kill enemies, gain coins, buy a sword. Every one of those is a system, and every system is a thing the player can learn.

    Why this matters: if you design systems instead of scenes, you can change your game late without breaking it. A scene is a fixed piece of content. A system is a rule you can tune with one number.

    The core loop

    The core loop is the shortest cycle of actions the player repeats. Move, fight, collect, upgrade, repeat. Everything else in the game exists to feed that loop or to interrupt it.

    A good core loop has three parts: a goal, an obstacle, and a reward. Kill the enemy (goal), it shoots back (obstacle), it drops coins (reward). Then the coins buy a better gun, which changes the next loop.

    The mistake almost everyone makes: building a loop that is fun for thirty seconds and then repeats identically forever. The fix is not more content — it is making the reward change the next loop.

    💡 Professor's Tip

    The core loop is the only thing that has to be fun. If the core loop is fun, you can add a menu, a story, and a soundtrack later and the game will still work. If the core loop is boring, no amount of content saves it.

    Game Feel and Juice

    Why some games feel amazing and others feel dead

    ▼

    What juice actually is

    Juice is the layer of extra feedback on top of your mechanics. The mechanics say the enemy died. The juice makes you FEEL it: a particle burst, a screen shake, a hit sound, a brief freeze, a score popup.

    None of these change the rules. The enemy dies exactly the same way with or without them. But without them the game feels like a spreadsheet, and with them it feels like a game.

    The reason beginners skip juice is that it feels like decoration — and decoration is what you add when the game is finished. Juice is not decoration. It is how the player reads the state of the game without thinking.

    The five cheapest sources of juice

    Screen shake: the single highest impact-to-effort ratio in games. A tiny camera offset on impact reads as weight.

    Hitstop: freeze the simulation for 60-80 milliseconds on a heavy hit. It reads as force.

    Particles: one burst on any important event — death, pickup, landing, hit.

    Sound: even a badly chosen sound beats silence, because it confirms the event happened.

    Anticipation: make the character crouch for a few frames before jumping. The player's eye follows the intent, not the movement.

    💡 Professor's Tip

    Do not add juice to everything. Juice marks the events that matter. If a pickup and a boss death get the same reaction, the player learns that nothing is special.

    Tick each box only when you have actually done it. These are not reading tasks.

    • Added a 60-80ms hitstop to the same impact

    • Anticipation makes movement readable.
    • Every event the player cares about needs a reaction.

    Player Psychology

    What keeps people playing, and what makes them quit

    ▼

    The two engines: mastery and curiosity

    Players keep playing for one of two reasons. Mastery: I am getting better at something and I can feel it. Curiosity: I want to know what happens next.

    Mastery is served by clear goals, immediate feedback, and a difficulty that rises as the player improves. Curiosity is served by revealing information slowly and by leaving questions unanswered.

    The failure mode is mixing them badly: a game that reveals everything immediately has no curiosity left, and a game with no clear goal has no mastery. Give the player one of the two at all times.

    The near-miss and the dopamine loop

    Players tolerate losing far more readily when the loss feels close. Losing 9-10 feels like "almost." Losing 0-10 feels like "never had a chance." This is why difficulty tuning is a psychology problem, not a numbers problem.

    The reliable reward loop: action, feedback, small reward, slightly bigger goal. Variable rewards — sometimes a big drop, usually a small one — hold attention longer than fixed ones, which is why loot exists and why it is easy to overuse.

    Be honest with yourself about which you are building. A loop that exists only to keep someone clicking is a slot machine, and players feel it.

    💡 Professor's Tip

    The single most common reason players quit a beginner game is not difficulty — it is not knowing what to do next. Fix clarity before you fix balance.

    Difficulty Curves

    Why most beginners get them wrong

    ▼

    The curve is a promise

    Difficulty should rise with skill. That means the curve is not a property of the game — it is a property of the player. The same level is easy for an expert and impossible for a beginner.

    A healthy curve looks like a staircase with flat landings: rise, rest, rise, rest. Each landing is where the player masters the new thing before the next challenge arrives.

    Beginners build a ramp — a constant gentle increase — because it feels safe. But a ramp has no landings, so the player never gets to consolidate. They are always slightly behind.

    Five ways to tune difficulty

    Enemy speed: the biggest dial. It changes how much time the player has to react, which changes everything.

    Enemy health and player damage: how many hits to win and how many to lose.

    Reaction windows: how long the player has to dodge or parry.

    Resource pressure: how often the player finds health, ammo, or currency.

    Checkpoint spacing: the real difficulty of a platformer is never the enemies, it is how far back you restart.

    💡 Professor's Tip

    Playtest with someone worse than you at games. If they can get through a section, anyone can. If you have to explain it to them, the problem is the game, not the player.

    🔄 Revision exercise: Write down the hardest moment in your game. Then list three number changes that would make it fairer without removing the challenge. Explain why numbers beat redesign for difficulty.

    Level Design Without Text

    Teaching mechanics by building, not by writing

    ▼

    The three-beat teaching pattern

    Every new mechanic should be taught in three beats. First, a safe introduction: the player meets it when nothing can go wrong. Second, a test: they must use it to proceed. Third, a twist: the mechanic combines with something they already know.

    If you skip the safe introduction, the player learns by dying. If you skip the test, they never learn at all. If you skip the twist, the mechanic stays isolated and they forget it.

    This is why good games do not have tutorials. They have rooms.

    Affordance and readability

    Affordance is what an object invites the player to do. A red barrel invites being shot. A ledge invites jumping. A glowing door invites entering. The player should never have to guess.

    Readability is whether the player can see the important thing. That means contrast, clear silhouettes, and nothing moving in the background behind the platform they are about to land on.

    The classic beginner mistake is a level that is visually rich and mechanically unreadable. Players do not fail because they lack skill — they fail because the game hid the information.

    💡 Professor's Tip

    The player's eye goes to whatever is brightest, biggest, or moving. Use that. Make the path brighter than the decoration and you will never need a tutorial arrow.

    Pacing and the First 60 Seconds

    Rhythm, tension, and the moment that decides everything

    ▼

    The first 60 seconds

    Players decide in the first minute whether they are staying. That minute must contain three things: a clear goal, one success, and one moment of curiosity.

    A common failure is a slow opening — walking through a quiet area, reading text, watching a cutscene. By the time the game starts, the player has already left.

    The fix is not to add action. It is to make the first thing the player does meaningful. Let them move, let them succeed at something small, and show them one thing they do not yet understand.

    Pacing: tension and release

    Pacing is the rhythm of tension and release. A fight raises tension. A quiet room after it releases it. Without the release, the fight stops feeling intense — the player goes numb.

    This is why games have safe rooms, hub areas, and dialogue breaks. They are not filler; they are the silence that makes the music audible.

    A useful test: if every section of your game is equally intense, none of it is.

    💡 Professor's Tip

    When in doubt, cut the opening. You can always add it back. Almost every beginner game starts two minutes too early.

    Movement Mechanics

    Run, jump, dash — and why jump feel matters more than jump height

    ▼

    The physics of feeling

    Platformer movement is not about physics accuracy. It is about three numbers: how fast you accelerate, how fast you stop, and how high you go. Games that feel good tune all three.

    The mistake is tuning gravity and jump height independently. What the player actually feels is the ratio between them: how long the jump hangs at the top, and how fast it falls back down.

    A jump that feels good usually has a faster fall than rise. The character rises gently and drops decisively. That asymmetry reads as weight.

    Coyote time and jump buffering

    Coyote time: let the player jump for about 0.1 seconds after they have walked off a ledge. Without it, a jump pressed a frame too late fails and feels like the game ate the input.

    Jump buffering: if the player presses jump slightly before landing, remember it and fire on landing. Without it, a well-timed jump on a moving platform fails silently.

    Both are about ten lines of code and both are the single most common reason a platformer feels broken. Players do not notice when they are there. They absolutely notice when they are not.

    Variable jump height

    Let the jump height depend on how long the button is held. A tap gives a small hop; a hold gives a full jump. This single change makes platforming feel dramatically more controllable.

    The implementation is simple: while the button is released and the character is still rising, apply extra gravity. Done.

    Players use this without ever being told. It turns an all-or-nothing jump into a tool.

    💡 Professor's Tip

    Play your movement with your eyes closed for thirty seconds. If you can feel where the ground is, the timing is right. If you are guessing, you need more coyote time.

    Combat Mechanics

    Hitboxes, telegraphs, and making fights readable

    ▼

    Readability is the whole fight

    A fight is won or lost on readability, not on damage numbers. The player must be able to answer three questions instantly: where is the enemy, what is it about to do, and what can I do about it.

    Telegraphs are the answer to the second question. Before an enemy attacks, it should visibly wind up — a crouch, a colour flash, a sound. The wind-up IS the information.

    The universal mistake: attacks that are instant and untelegraphed. The player cannot dodge what they cannot see coming, so the fight becomes memorisation rather than skill.

    Hitboxes, hurtboxes, and i-frames

    The attacker has a hitbox (where the damage comes from) and the defender has a hurtbox (where they can be hit). Keeping the hurtbox smaller than the sprite makes the game feel forgiving; keeping it larger makes it feel punishing.

    Invincibility frames (i-frames) after taking damage prevent the player being hit twice by one swing. Almost every action game uses them. Without them a single enemy attack can drain a full health bar.

    Both are invisible to the player and both change how the game feels more than any damage number.

    Making enemies interesting with three behaviours

    You do not need ten enemy types. You need one enemy with three states: idle, telegraph, attack. Then a second enemy that does it faster, and a third that does it from a distance.

    Depth comes from combinations, not from variety. A fast enemy plus a ranged enemy in the same room is a new encounter without a new asset.

    Design the encounter, not the monster.

    💡 Professor's Tip

    If the player dies and says "that was cheap", the fault is almost always a missing telegraph. Add information before you add difficulty.

    • Built one encounter from two enemy types instead of one new type

    Enemy and Background Characters

    NPCs, crowds, and ambient life that makes a world feel inhabited

    ▼

    Why background characters matter

    A world with only the player and enemies feels like a test chamber. A world with people walking, working, and talking feels like a place — even if none of them do anything.

    The trick is that ambient characters need almost no behaviour. A villager who walks between two points and says one line is enough. The player's brain fills in the rest.

    This is the cheapest worldbuilding in games: one sprite, two waypoints, one line of dialogue.

    NPC behaviour on a budget

    Full AI is expensive. Budget AI is a state machine with three states and no pathfinding: patrol, notice, react. The NPC walks a route, notices the player within a radius, and says something.

    Give each NPC one rule that makes them memorable. The blacksmith sharpens the same sword every thirty seconds. The guard always looks the wrong way. One rule is enough.

    Players remember NPCs with one quirk far longer than NPCs with complex behaviour.

    Crowds and density

    A crowd is just many simple characters with different speeds. The illusion of a busy place comes from density and variety, not from intelligence.

    Keep crowds away from the critical path. Crowds that block the player's route turn atmosphere into frustration.

    Layer your density: a few characters close and interactive, many far away and decorative. The far ones can be cheaper.

    💡 Professor's Tip

    Ambient characters should never be required for progression. If the player can fail because an NPC walked into the wrong place, you have built a bug, not a world.

    Economy, Progression, and Rewards

    Making the player feel they are getting somewhere

    ▼

    Progression is a promise

    Progression is the player's answer to "why am I still playing?" It must be visible, regular, and slightly ahead of them.

    The most reliable structure: small rewards every few minutes, a medium reward every level, and a large reward at the end. If the player can see the next reward, they will keep going.

    The failure mode is a long gap with nothing. Players do not quit at hard parts — they quit at empty parts.

    Designing a simple economy

    An economy is just two flows: the player earns a resource and spends it. The design question is what the spending choice means.

    If there is only one thing to buy, there is no economy — there is a queue. Give the player at least two competing uses for the same resource: damage or defence, speed or health.

    Every purchase should cost the player something they wanted. A choice with no trade-off is not a choice.

    Level-ups without a skill tree

    You do not need a branching skill tree. Three meaningful upgrades chosen from a small list is enough, and it is far easier to balance.

    Make upgrades change how you play, not just how hard you hit. A jump that goes further changes your routes. A bigger number changes nothing.

    The best upgrades are the ones the player notices without reading the description.

    💡 Professor's Tip

    If the player cannot say what they are saving for, they will stop earning. Always show the next reward.

    • Given one currency at least two competing uses

    • Checked the player can name what they are working toward

    State Machines and Game Flow

    Organising behaviour so it stops becoming spaghetti

    ▼

    Why state machines

    Any character that does more than one thing will eventually become a tangle of if-statements. A state machine replaces the tangle with a list of states and the rules for moving between them.

    The minimum useful version: an enum of states, and a match statement in your update function that handles each one. That is the whole pattern.

    The value is not elegance — it is that you can now see, in one place, every state the character can be in and every transition. Bugs live in the transitions you forgot.

    Legal and illegal transitions

    Write the transitions down as a table before you code: from each state, where can you go? Then make everything else illegal and handle it.

    The most common bug is a state that cannot be exited — an enemy stuck in its wind-up because the interruption was not defined. If you can get into a state, you must be able to get out.

    Guard clauses are your friend: if a state is entered and its exit condition is never checked, the game soft-locks.

    Game flow: menu, play, pause, game over

    Game flow is the same pattern one level up. Your game has states too: menu, playing, paused, game over, victory. Each has rules for entry and exit.

    The beginner mistake is building each screen as a separate scene with no shared flow logic, so the pause screen forgets to actually pause, or the game-over screen cannot return to the menu.

    Define the flow once, in one place, and let every screen read from it.

    💡 Professor's Tip

    When a bug appears in a state machine, do not add another if. Add the missing transition to the table first. Most state bugs are missing rules, not broken code.

    ✅ Your Task — Revision Checklist

    Tick each box only when you have actually done it. These are not reading tasks.

    Boss Design

    Phases, tells, and making a finale feel earned

    ▼

    A boss is a test, not a wall

    A boss fight is an exam on everything the player has learned. That is the whole design brief: every mechanic from the game should appear in the fight at least once.

    If the boss uses a mechanic the player has never seen, the fight is unfair. If it uses nothing new, it is a damage race. The sweet spot is familiar mechanics under new pressure.

    This is why the best boss fights are usually the ones right after the best teaching level.

    Phases and escalation

    Give the boss two or three phases, each faster or more aggressive than the last. The phase change should be visible — a colour shift, a new attack, a change in the arena.

    Phases solve the pacing problem of a long fight: the player gets a clear sense of progress, and the fight can escalate without becoming unfair.

    The phase transition is also a natural breather. Give the player a moment of release between phases.

    The final blow

    The killing blow should feel different. Slow it down, play a distinct animation, give the player a moment where nothing can hurt them.

    This is not polish for its own sake — it is the payoff for the whole fight. A boss that dies the same way as a normal enemy wastes the fight you just built.

    The player should be able to tell, without the health bar, that they won.

    💡 Professor's Tip

    Play your boss fight and count how many times the player must use a skill from earlier in the game. If the answer is zero, the fight is not testing anything.

    Why You Don't Need to Draw

    Programmer art, silhouettes, and looking intentional

    ▼

    The myth of the artist

    Almost every developer starting out believes they must draw before they can make a game. It is false, and it stops more games than bad code does.

    Games are made from primitives all the time. A rectangle with a face is a character. A circle is a coin. A coloured square is a tile. Players do not judge your art by its complexity — they judge it by whether it is consistent and readable.

    The bar is not "good art". The bar is "intentional art" — art where every choice was deliberate. A clean limited-palette game beats a messy detailed one every time.

    The silhouette test

    If you cannot tell what a character is from its solid black outline, the player cannot read it in motion. This is the single most useful art test in games.

    Apply it: fill your character solid black. Can you still tell it apart from the enemy? Can you tell whether it is jumping or running? If yes, your shapes are working.

    Good silhouettes come from exaggeration. Make the hat bigger, the shoulders wider, the weapon longer. Exaggerated shapes read better at small sizes.

    One accent colour

    Limit yourself to a background colour, a main colour, and ONE accent colour. The accent is for things the player must notice: the player, the goal, the danger.

    When everything is accent-coloured, nothing is. Restraint is what makes the accent work.

    This is a rule you can follow with no artistic judgement at all: pick three colours and never add a fourth.

    💡 Professor's Tip

    Pixel Art for Non-Artists

    Piskel, Aseprite, and the 16x16 workflow

    ▼

    Start at 16x16, not 64x64

    Small canvases are forgiving. At 16x16 you have 256 pixels; a character is maybe twelve of them. Every decision is visible and nothing can hide.

    The beginner mistake is starting big and getting lost. A 16x16 character that reads well is worth more than a 64x64 character that reads as noise.

    Free tools: Piskel (browser, no install), Libresprite (free, desktop), Aseprite (paid, excellent, compile-free builds available). All three handle pixel art fine.

    The pixel art workflow

    Draw the silhouette first as a solid block of the main colour. Then carve the inside with one shade darker and one shade lighter. Then add the accent colour last.

    Shading rule that always works: light comes from above, so the top edge is lighter and the bottom edge darker. You do not need to think about lighting — just follow the rule.

    Outlines are optional. Many good pixel art styles skip them entirely and rely on contrast instead.

    Animation with two frames

    You do not need twelve frames. A walk cycle of two frames — legs apart, legs together — reads as walking. An idle animation of two frames — normal, slightly lower — reads as breathing.

    Frame timing matters more than frame count. Two frames at 6 frames per second looks better than six frames at 2 frames per second.

    Test at the size the player will actually see it. Animation that looks good large often looks broken small.

    💡 Professor's Tip

    Zoom out to the actual game size constantly while you draw. Pixel art that only looks good zoomed in is not finished.

    Vector Art and Free Asset Libraries

    Inkscape, shapes, and using other people's art honestly

    ▼

    Vector art is shapes, not drawing

    Vector art is built from primitives: rectangles, circles, and paths combined. You never draw a line freehand — you move points until a shape looks right.

    Inkscape is free and does everything a beginner needs. The three operations that matter: union (merge shapes), difference (cut one shape out of another), and intersection (keep only the overlap).

    With those three you can build any icon, any UI element, and most simple characters. It is closer to construction than to drawing.

    Where to get free assets

    Kenney.nl — thousands of public-domain (CC0) assets: UI packs, platformer tiles, characters, audio. No attribution required, commercially usable.

    OpenGameArt.org — huge range, but every file has its own licence. Always check it. CC0 and CC-BY are safe; CC-BY-SA has share-alike obligations.

    itch.io has a large free-assets section, often with clear licensing on the page.

    Your own engine ships with assets too — Godot's icon.svg is a perfectly good placeholder.

    Using assets honestly

    Read the licence every time. "Free" and "free to use in your game" are not the same thing.

    Keep a text file listing every asset you use, where it came from, and its licence. Future you will need it the moment someone asks.

    Never asset-flip: reselling an unmodified asset pack is both unethical and, on most platforms, banned.

    Mixing asset packs from different authors looks bad. Pick one style and stay with it.

    💡 Professor's Tip

    If you cannot find the licence for an asset, do not use it. There is always another asset.

    3D to 2D, Procedural Art, and Code-Drawn Graphics

    Getting sprites without drawing a single frame

    ▼

    Render 3D models into 2D sprites

    Blender is free and can render any model into a flat sprite sheet. You build or download a simple model, set up an orthographic camera, and render the animation frames.

    This is how many small teams get character art without an artist. A low-poly model with flat colours renders into clean, consistent sprites that all match because they come from the same source.

    You can also download free low-poly models and render them yourself, which avoids both drawing and modelling.

    Procedural and code-drawn art

    Everything in a game can be drawn by code. Godot's draw_ functions let you draw rectangles, circles, polygons, and lines every frame — no image files at all.

    This is genuinely practical for UI, for backgrounds, for graphs, for any abstract visual. A bar chart, a health bar, a grid — all trivially code-drawn.

    Shaders extend this: you can generate patterns, gradients, noise, and entire backgrounds from maths. A fragment shader that draws a starfield is about fifteen lines.

    Generated textures

    Noise is the foundation of most generated texture. A grid of random values smoothed together gives you clouds, marble, terrain, and rust.

    You do not need to understand the maths to use it. Most engines expose noise as a single function call that returns a value between 0 and 1 for a given position.

    Tile it, scale it, threshold it — and you have a texture that is unique to your game and cost you nothing.

    💡 Professor's Tip

    Code-drawn visuals have one enormous advantage: they scale perfectly. A code-drawn health bar looks identical at every resolution; an image-based one has to be redrawn for each.

    Animation Without Animating

    Tweening, squash and stretch, and faking it convincingly

    ▼

    Tweening does the work

    A tween moves a value from A to B over time. That one mechanism produces most of what beginners think of as "animation": movement, scaling, fading, colour changes, rotation.

    You do not need to keyframe anything. You say where it starts, where it ends, and how long it takes. The engine interpolates.

    This is why a game with no animation frames can still feel alive. A health bar that tweens down reads as damage far better than one that snaps.

    Squash and stretch

    Squash on landing, stretch during a jump. It is the oldest animation principle in games and it still works.

    The rule: the volume stays roughly constant, so when you squash wide you also squash short. When you stretch tall you also stretch thin.

    Two lines of scale code. The player reads it as weight and impact without ever noticing it consciously.

    Fake animation from primitives

    A character that is a circle can "walk" by wobbling. A box can "attack" by stretching toward the target. A coin can "spin" by scaling its width from full to zero and back.

    The principle: any motion that implies intent reads as animation. The player's brain completes the rest.

    This is not a compromise — it is a legitimate style. Many successful games are built entirely on it.

    💡 Professor's Tip

    Animate the state change, not the object. A door that tweens open communicates more than a door with a twelve-frame animation.

    UI, Sound, and Levels Without Skills

    Three things beginners think need talent, and the rules that replace it

    ▼

    UI design rules that always work

    Alignment: pick one edge and put everything on it. Misaligned UI looks broken even when every element is good.

    Spacing: use the same gap everywhere. Consistency in spacing is what makes UI look designed.

    Hierarchy: the most important thing is the biggest or the brightest. If everything is equally prominent, nothing is.

    Contrast: text must be readable against its background at a glance. If you squint and cannot read it, it fails.

    All four rules are mechanical. You can follow them without any design sense.

    Sound without making any

    Free sources: the same CC0 libraries that serve art often serve sound. Freesound.org has a large collection, but every file has its own licence — check it.

    Synthesis: tools like sfxr and its modern equivalents generate retro sound effects from sliders. You do not need to understand sound design to get a usable jump sound.

    Rules that matter more than the sounds themselves: every event the player cares about needs a sound, repeated sounds must vary in pitch, and silence after a big event makes the next sound land harder.

    Levels and tilemaps without art skills

    A tilemap is a grid where each cell holds a tile. You do not need art to make one — you need a small set of clearly different coloured tiles.

    Design rule: the walkable tile and the solid tile must be distinguishable at a glance. If the player cannot tell where they can walk, the level has failed before it began.

    Build the level with placeholder tiles first and play it. Only replace the tiles once the layout is fun. Art on an unfun level is wasted art.

    💡 Professor's Tip

    For all three: build the functional version first and make it look right second. A working ugly UI beats a beautiful broken one.

    Scoping a Game You Can Finish

    The design skill that decides whether your game exists

    ▼

    The maths of finishing

    Estimate your game in the smallest unit you can build: one room, one enemy, one level. Then multiply by how many you need. Most beginner projects die on this multiplication.

    A game with ten levels, five enemy types, and three bosses sounds modest. At one level per week that is ten weeks before content is done — before polish, before bugs, before the menu.

    The professional move: build one level completely, with polish, and call that the game. Everything else is a stretch goal.

    Cutting without losing the game

    Cut in this order: extra enemy types, dialogue, save systems, extra levels, side content. Never cut the core loop, the menu, or the game-over screen.

    The test for what to cut: does removing it change what the player does? If not, it can go. A second enemy type that behaves identically is not content.

    Cutting is not failure. Shipping a small complete game is a success; finishing a large broken one is not.

    The smallest shippable version

    Define the smallest version of your game that is still a game: one mechanic, one level, one goal, a menu, and an ending. That is your target. Everything else is stretch.

    This is not pessimism — it is how you guarantee a finished project. A small game you finish teaches you more than a large one you abandon.

    Write the smallest version down before you write any code. It is your promise to yourself.

    💡 Professor's Tip

    Every feature you add after the smallest shippable version must earn its place by changing what the player does.

    Playtesting That Actually Finds Problems

    The method professionals use, and the mistakes that ruin it

    ▼

    Watch, do not help

    The single most important rule: say nothing while they play. Every hint you give invalidates the test, because you have just fixed the problem you came to find.

    Your job is to observe and record. Where did they hesitate? Where did they look confused? Where did they do something you did not expect?

    Hesitation is the most valuable signal you will get. It almost always means the game failed to communicate.

    Ask the right questions

    Wrong: "Did you like it?" This gets politeness, not information.

    Right: "What did you expect to happen?" This gets you their mental model, which is what you need.

    Right: "What were you trying to do just then?" This reveals the gap between your intent and their understanding.

    Never ask leading questions. If your question contains the answer, it is not a question.

    Recording and triaging

    Write down every problem immediately. Memory is unreliable and you will lose the small ones, which are often the important ones.

    Group problems: confusion, difficulty, bugs, and feel. They need different fixes.

    Fix confusion first. It is the cheapest to fix and the most damaging if left.

    You do not need many testers. Three to five people find the vast majority of issues.

    💡 Professor's Tip

    If you can only get one person to playtest, watch them in silence and take notes. That single session is worth more than ten opinions.

    ✅ Your Task — Revision Checklist

    Tick each box only when you have actually done it. These are not reading tasks.

    • Watched someone play for five minutes without helping
    • Written down every hesitation and confusion point
    • Asked "what did you expect to happen?" rather than "did you like it?"
    • Sorted every problem into confusion, difficulty, bug, or feel
    • Fixed a confusion problem before anything else

    Iteration and Shipping

    The loop professionals actually use, and how to finish

    ▼

    The iteration loop

    Build a tiny thing, play it, change it, play it again. That loop is the entire method.

    The mistake is building for weeks before playing. A game you have not played in a month has problems you cannot see, and they compound.

    Playable beats planned. A rough playable build every week teaches you more than a perfect design document.

    Each pass should have exactly one goal. "Make the jump feel better" is a pass. "Improve the game" is not.

    The last ten percent

    The final stretch is where games are actually finished: the menu, the pause, the game-over screen, the export, the icon, the credits.

    None of it is glamorous and all of it is required. A game without a working quit button feels broken no matter how good the levels are.

    Make a shipping checklist at the start of the project and work through it at the end. Future you will be tired and will forget things.

    Testing the export

    Always test the exported build, not just the editor. Missing assets, broken paths, and audio that only works in the editor all appear exclusively in the export.

    Play the exported executable on a clean machine if you can. Problems that do not reproduce on your development machine are the ones your players will hit.

    Keep the export and the source in sync. An export from two months ago is not your game.

    💡 Professor's Tip

    Finish the checklist, then stop. There is always one more improvement, and the discipline to stop is what separates finished games from abandoned ones.

    Case Studies: How Great Games Are Made

    What actually made these games work

    ▼

    Celeste: difficulty as an option

    Celeste is a hard platformer that anyone can finish. The assist mode lets players change game speed, stamina, and invincibility — and using it is not treated as failure.

    The lesson is not that you must build an assist mode. It is that difficulty and accessibility are separate design problems, and a hard game can still be a fair one.

    Its movement is also a masterclass: coyote time, jump buffering, variable jump height, and a dash that resets on landing. Every one of those is in this course.

    Undertale: economy of content

    Undertale is famous for writing, but its real achievement is that almost every system feeds the same combat. Bullets, dialogue, mercy, and fighting all run through one interface.

    The lesson: one system used five ways beats five systems used once. It is cheaper to build and the player learns faster.

    Look for the system in your game that could do a second job before you build a new one.

    Stardew Valley: scope and systems

    One developer, four years, and a game that looks simple. The secret is that almost everything is data-driven: crops, friendships, and festivals are tables, not code.

    The lesson for a beginner: if you can express a feature as data instead of code, you can add a hundred of them. Design your systems so content is a spreadsheet row, not a new function.

    This is the single highest-leverage design habit a small developer can build.

    💡 Professor's Tip

    Do not copy what these games look like. Copy how they are structured — one system, many uses; data instead of code; difficulty as an option.

    Designing a Character You Cannot Draw

    From a one-sentence idea to a sprite that reads

    ▼

    Start from the verb, not the look

    Begin with what the character does, not what it looks like. "A fast scout" gives you a silhouette: small, light, forward-leaning. "A heavy guardian" gives you the opposite.

    This matters because beginners start with appearance — a colour they like, a weapon that looks cool — and end up with a character that communicates nothing at a glance.

    Write the verb first. The silhouette follows from it almost automatically.

    Three shapes and a colour

    A readable character needs only three shapes: a head, a body, and one distinctive feature. Everything else is noise.

    The distinctive feature is what the player remembers. A big hat, a long weapon, a glowing eye, a tail. Pick one and exaggerate it.

    Then pick one colour for the character and one accent. The accent is for the one thing that must be noticed.

    The silhouette and expression test

    Fill the character solid black and check you can still tell it apart from every other character in the game. Then check the same silhouette reads when scaled to half size.

    Expression without a face: posture communicates more than features. A character leaning forward reads as determined; one hunched reads as tired. You can convey mood with the body alone.

    If the player can read the character's state from the silhouette, the art has done its job.

    Naming and one sentence of backstory

    A name should be sayable and should hint at the verb. A fast scout should not be called something that sounds heavy.

    One sentence of backstory is enough: "She maps places no one else will go." That sentence should explain the silhouette. If it does not, the design and the story are fighting.

    Backstory exists to justify design decisions, not to be read.

    💡 Professor's Tip

    Design the character for the size they appear in your game. A character seen at 32 pixels cannot have a detailed face — so do not draw one.

    Making Maps, Worlds, and Levels

    Layout principles that work without artistic skill

    ▼

    Levels are a sequence of reasons to be there

    A level is not a series of rooms. It is a series of reasons for the player to move forward. If a room has no reason to exist, merge it into a neighbour.

    Before placing any tile, write the level as a sentence: "Enter, cross the gap, fight on the platform, climb to the exit." Then build only those beats.

    This is how you design a level without art: the layout carries the experience, and the art decorates it.

    The critical path and the optional branch

    Every level needs one critical path — the route the player must take — and it must be identifiable at a glance. Optional branches are where the rewards live.

    Mark the critical path with your brightest tile or strongest lighting. The player's eye should land there before it lands anywhere else.

    Branches should be visible but not obvious. The player should feel clever for finding them, not punished for missing them.

    Teaching through geometry

    Geometry teaches. A gap the player can barely clear teaches jumping. A gap that is impossible teaches nothing except that the game is unfair.

    Introduce a new movement requirement at its easiest, then increase it. A small gap, then a wide gap, then a gap with an enemy in it.

    The level is the tutorial. If you need a text box, the geometry has failed.

    Scale, density, and emptiness

    A common beginner level is uniformly busy — every room the same size, the same density. It reads as flat.

    Vary the scale deliberately: a tight corridor, then a wide open room. Contrast makes both feel bigger.

    Leave some space empty on purpose. Emptiness is a design tool, not a gap in your work.

    💡 Professor's Tip

    Build the level from grey placeholder tiles first and play it before making any art. If the layout is not fun with grey boxes, no amount of art will fix it.

    UI, Menus, and Player Onboarding

    The parts players see first and judge fastest

    ▼

    Menus are part of the game

    Players meet your main menu before they meet your game. A menu that is slow, unresponsive, or unclear sets the expectation that the game will be too.

    The three rules: every button must respond instantly, the first option must be focused so a keyboard or controller works, and there must always be a way back.

    A menu is a user interface problem, not an art problem. Apply the four mechanical UI rules from Day 50 and it will look fine.

    Onboarding without a tutorial screen

    The best onboarding is not a tutorial screen — it is a first level that teaches by being played. But you still need a first minute that works.

    Structure the first minute as three beats: let the player move freely, let them succeed at something small, then show them one thing they do not yet understand.

    Never open with a wall of text. Players do not read at the start; they read when they are stuck.

    HUD and information design

    The HUD should answer the questions the player actually asks: how much health, how much ammo, where am I going. Anything else is decoration.

    Keep it in the corners, keep it small, and keep it consistent. A HUD that moves around the screen forces the player to search for it.

    Show information only when it changes. A health bar that is always full is noise; one that appears when you take damage is information.

    Settings, accessibility, and saving

    Every game needs volume controls, a way to remap or at least confirm controls, and a way to turn off screen shake. Shake in particular makes some players physically unwell.

    Saving should be invisible. If the player has to think about saving, the save system is too prominent.

    Accessibility options are not extra features. They decide whether some players can play at all.

    💡 Professor's Tip

    Test your menu with a stopwatch. If it takes more than three seconds to get from launch to playing, the opening is too slow.

    The Road From Here

    What to build next, and how to keep improving

    ▼

    Ship, then start again

    The single most important habit: finish something small. One finished game teaches more than five abandoned ones, because finishing includes the parts tutorials skip — the menu, the bugs, the export.

    After your first game, make a second one in half the time using the same skills. You will be surprised how much faster you are, and the second one will be noticeably better.

    Do not start a large project next. Start a small one, finish it, and let the scale grow naturally.

    Where to learn next

    Shaders: a canvas shader adds enormous polish for very little code, and it is the natural next step after you are comfortable with nodes and scenes.

    Reading other people's work: the official demo projects are free and well-commented. Reading working code teaches you structure that tutorials do not show.

    Design, not just code. The gap between good and great is almost always design. Study why games feel the way they do, not just how they are built.

    Joining a community

    Game jams are the fastest way to improve. A deadline forces you to finish, and the theme forces you to be original rather than imitate.

    Share your work early and often. Feedback at the rough stage is far more useful than praise at the end, and it is easier to act on.

    Helping others with their problems teaches you more than solving your own, because you see approaches you would never have tried.

    Your personal checklist

    After thirty days of Godot and thirty days of design, you should be able to: build a small complete game, tune how it feels, make art without drawing, design a level that teaches itself, and finish.

    Keep a personal checklist of the habits that matter: finish small things, playtest in silence, cut before you add, and ship the export.

    The habits are the curriculum. The games are just the practice.
